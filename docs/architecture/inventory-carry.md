# Player inventory and storage carrying capacity

Player inventory consists of durable quantity balances and distinct owned instances. It has no grid, numbered inventory positions, manual stacks, or commodity maximum stack size. Manor Storage and City Warehouse use the same kilogram weight convention with fixed capacities of 10,000 kg and 1,000 kg. Their retained slot positions are ordering metadata only and never limit storage.

## Authoritative quantities and identity

- `player_inventory` is the commodity ledger, uniquely keyed by player, resource type, and the exact variant string. Its `entry_id` identifies one logical balance regardless of quantity. Existing `stackId` request fields are compatibility aliases for that entry UUID; they do not identify a limited stack. Partial drop, deposit, donation, sale, consumption, and crafting debit the requested quantity directly.
- Equipment remains in `equipment_instances`, preserving UUID, condition, item level, enhancement identity, metadata, ownership/custody, and saved-kit references. Equipment is never combined by definition ID. Backpacks remain distinct `player_backpack_instances` with their ownership and storage/equip locations.
- Quantities use PostgreSQL bigint, server bigint arithmetic, and validated safe-integer wire quantities. Weight sums use PostgreSQL numeric and server bigint. Decimal strings carry total grams over the wire without floating-point coercion. Kilograms are a display conversion only.

## Weight and transaction boundary

The configurable item weights, backpack unit weight, and storage capacities live in `packages/shared/src/inventoryWeight.ts`. The initial personal baseline is 1,000 kg. Migration 0829 seeds PostgreSQL weights from that catalog; migration 0830 raises retained personal baselines and moves Manor/City storage to 10,000 kg and 1,000 kg. Startup item validation rejects divergent item weights. All on-person commodities, equipment, and backpacks are included in the weight query, including equipped instances; backpacks contribute zero own grams by contract. Stored, escrowed, collected-market, destroyed, and ground items do not count. Equip/unequip cannot make item weight disappear.

Every mutation locks its player's `player_inventory_capacities` row. PostgreSQL BEFORE triggers capture the starting weight/capacity before a balance or instance mutation, acquiring both owner locks in sorted order for an ownership transfer. Deferred constraint triggers check the final transaction weight. InventoryService performs early admission and preserves the existing operation/event ledger and replay checks; the database guard also covers direct equipment and backpack writes. Multi-resource failure rolls the whole transaction back. SQL carry violations use constraint `player_inventory_carry_capacity` and map to the same clean gameplay capacity errors.

Crafting consumes inputs before admitting output. The final transaction must fit the new capacity. A player migrated above the limit retains every item and may reduce weight or perform a net non-increasing transaction while maximum capacity is not reduced. Positive net additions remain blocked until enough weight is removed. Unequipping a backpack cannot lower capacity below carried weight. There are no movement penalties.

## Backpack progression

Each owned backpack stores `upgrade_level` explicitly from +0 through +10; the four established equipped backpack positions remain. `BACKPACK_LEVELS` in `packages/shared/src/backpacks.ts` defines the exact craft/upgrade costs, `5,000 * (level + 1)` gram capacity bonus, and an empty effects object. PostgreSQL `backpack_level_definitions` mirrors it and startup validates the levels. A backpack's own carried weight is zero; only its equipped capacity bonus affects the owner's maximum. Future configured per-level effects need no progression schema replacement; this feature applies only capacity.

Maximum grams equal the player's base grams plus the bonuses of equipped backpack levels; at most four equipped instances contribute. Migration 0849 gifts every existing backpack to +10 while preserving its instance ID, owner, and custody location. The shared legacy slot constants/named definitions remain historical decoding metadata and are not current capacity rules. Balance adjustments require a forward catalog migration plus the corresponding shared configuration update.

## Forward migration and compatibility

Migration 0829 first verifies exact equality between existing commodity balances and summed old slots, refusing a discrepancy rather than choosing a lossy winner. It keeps the canonical quantities and variants and reuses the earliest old stack UUID as each entry identity. Equipment state and all backpack ownership/IDs survive. The old grid becomes the read-only `legacy_player_inventory_slots` archive; live synchronization, maximum-stack validation, and position allocation are removed. Carried instance position columns are cleared and retired. Historical operation results remain intact, while current snapshots always include weight and explicit backpack levels. Migration 0830 promotes the retained Manor overflow ledger into active storage rows before dropping the old position uniqueness/range gates, so no stored quantities become inaccessible. Inventory revisions now advance from the balance table itself.

## Entry-point audit

Commodity additions use InventoryService across gathering/mines/fishing, loot and rewards, shops/market, crafted output and refunds, storage withdrawals, progression, expeditions, packages, and developer grants. Equipment starter/package/craft/limited-shop grants, ground pickup, market purchase/cancel/claim/reconciliation, and manor equipment/backpack withdrawal use the same carry lock/checks. Protection, drops, manor deposits, and city donations resolve canonical entry IDs. Retired player split/restack/move/reorganize commands return a clear retired-action error.

Explicit partial flows preserve existing custody: ground pickup leaves an unpicked remainder; oil wells retain stored output; production queues advance only collected units; package lines retain remaining quantities; supported refunds and physical rewards leave overflow in durable ground drops; bulk manor transfer records skipped/remainder amounts. Exact grants, purchases, and ordinary atomic additions reject excess weight without losing inputs or currency. Manor backpack storage moves the same `player_backpack_instances` row, retaining enhancement level, UUID, and ownership; the Goblin Market's existing backpack sale destroys only the selected carried instance after paying its offer. No player trade, backpack world-drop/pickup, or backpack-specific death-drop transition exists in the inspected production paths, so this feature does not invent a parallel transfer system.

Intentionally retained positions and limits belong to equipment equip positions, four backpack equip positions, crafting queues, shrines, and parties. Manor and City Warehouse slot positions remain only as stable ordering metadata; their kilogram capacities are the sole storage limits. Historical catalog/ground-drop max-stack metadata is not a player inventory capacity rule. No player-facing list quantity is split to satisfy a max-stack limit.
